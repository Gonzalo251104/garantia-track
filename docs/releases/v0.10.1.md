# v0.10.1

Release candidate prepared on 2026-11-06, America/Lima. The published application remains v0.10.0 until this candidate completes the release and Sites publication workflow.

## Mobile readability

- Form labels, editable controls and primary actions use 16 px text at the default root size. Secondary guidance, navigation, filters and status badges use at least 14 px. Text and status colors have stronger contrast.
- Narrow order cards wrap long model/customer names, give customer information its own row, and keep the status and order action available. Detail fields and status choices stack on mobile; filters and headings wrap.
- Reception has a direct heading, one required-field/fictional-pilot note and a concise photo hint. Decorative counter captions, repeated panel descriptions and pre-save wording that suggested changes were already saved are removed.
- General dashboard guidance about tracking links is available in a keyboard-accessible disclosure. Internal/public message visibility, photo privacy, upload limits, demo limitations and QR invalidation warnings remain visible.

The change was integrated through PR #62. This release preserves its runtime and tests; preparation changes only version, changelog and release-note metadata. No migration or dependency update is required. Thermal paper dimensions, print typography, PDF generation, scoped backend writes and existing tracking links retain their behavior.

## Evidence and limits

- Feature CI passed lint, syntax, all 113 existing tests and build on the reviewed head before merge. Require green CI on the release PR's own current head before integration into main.
- The actual frontend and bundled SDK were checked against an isolated loopback HTTP fixture with invented sign-in values and in-memory data. Demo checks were separate. No production orders, accounts, photos or tracking links were changed during this work.
- Checks at 320/390 px and landscape/desktop spot checks found no page-level horizontal overflow. Inspected application text was at least 14 px outside thermal paper; editable controls were 16 px and mobile navigation targets were 60 px tall. Long names, keyboard disclosure/radio interaction, required fields, demo Other intake and fixture status/message save/reload were checked.
- Demo tickets retained their 58/80 mm paper settings and 11/12 px paper typography while screen guidance was 14 px. Selected text/status color pairs had a minimum calculated contrast of 5.82:1. These are bounded checks, not a full accessibility audit, physical printing or physical iPhone/Safari acceptance.
- Reuse this unchanged feature evidence; see [mobile-readability.md](../mobile-readability.md). Reobserve reading and task comprehension on the technician's phone after publication. Keep the pilot fictional and existing photo-access, external email/recovery, independent backup/recovery and operational readiness gates open. Draft recovery PR #26 remains excluded.

## Publication checklist

1. Review the release PR into main and require green current-head CI. Merge through the PR, then wait for main validation and the immutable v0.10.1 GitHub tag/release. Record the canonical main commit. GitHub publication and Sites deployment are separate steps.
2. Use the current Sites workflow and existing public project. Synchronize approved main into the hosting mirror, build with the existing public configuration and canonical release commit, and package the runtime and hosting manifest. Include the new `dist/readability.css` referenced by `dist/index.html`, plus generated config/version/vendor assets. Exclude tests, SQL, fixtures, operator tools, environment files, backups and private links/data.
3. Save/deploy through supported Sites tools and verify terminal success. Match public version metadata and served assets to the approved release, including the new stylesheet. Refresh older open tabs.
4. In an authorized fictional workshop, inspect Orders, Reception, a saved order and Taller at narrow widths. Check readable labels, long-name wrapping, optional help and visible privacy/QR warnings. Use read-only views and unsaved fictional drafts; existing local persistence evidence does not require new production orders, status writes, photos or QR creation/rotation.
5. Keep sessions and private links in their original profiles. Record sanitized results and unchanged existing data/tracking metadata. Keep detailed operational receipts local and add a short product-level publication summary to GitHub.
6. Complete main to develop through a backmerge PR with green CI. Physical iPhone/Safari and any promised thermal printing remain separate follow-up checks.
