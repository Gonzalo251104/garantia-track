# Equipment types

PR #59 was merged into develop at `53c65169c84d8155faaab5ec15bc01b007590f63`. The option shipped in [v0.10.0](releases/v0.10.0.md), which records migration-before-frontend publication and compatible rollback steps.

## Pilot finding and scope

The test user requested an Other choice for intake. Reception now offers **Consola**, **Mando** and **Otro**, storing `console`, `controller` and `other`. Console remains the default. The existing required **Modelo** field identifies equipment such as a fictional racing wheel or charging base; choosing Other does not remove model/customer/contact/issue validation or add a second description field.

The choices form a labeled native radio group, support arrow-key navigation and have 48 px minimum targets with 16 px labels. They wrap on narrow screens. A shared type mapping validates intake and labels the order list and receipt projection. Other has a generic equipment icon in the list, order and tracking view. Unknown values display as Equipo rather than being mislabeled as a console/controller; unknown and null types are still rejected at intake and in PostgreSQL. CSV retains its current columns and includes the entered model. This does not add categories, custom taxonomy or type editing for saved orders.

## Migration and publication order

The original `repair_orders_device_check` admits only console/controller. The additive migration `supabase/migrations/20261106180602_other_device_type.sql` replaces that check atomically with the three-value allowlist. The existing NOT NULL column constraint stays in force. No row rewrite, function/grant/policy change, SDK/dependency update or key lookup is needed.

The file was generated by the already available official Supabase CLI 3.0.0 using local-only `migration new other_device_type`. An uncached npx lookup could not resolve the registry; no dependency installation or manifest change was made. The reviewed SQL was applied only to the isolated laboratory on 2026-11-06 (America/Lima), through the supported migration tool. The tool assigns its own lab history version; identify it by name and compare the SQL rather than replaying unrelated migrations.

After feature integration and a separately reviewed release, apply this exact migration to production **before publishing the new frontend**. Recheck the live constraint and existing migration history first; avoid a blind database push. Production remains on v0.9.1 with its original constraint during feature preparation. Refresh older open clients when rolling out: pre-feature clients can mislabel newly stored Other orders.

Do not narrow the database constraint after Other rows exist, or convert/delete records to force a rollback. A compatible fallback should hide the new intake choice while retaining Other display support and the expanded constraint. Redeploying pre-feature code can mislabel existing Other rows, so assess that limitation before using an old saved frontend. Keep QR capabilities, photos and all existing records intact.
